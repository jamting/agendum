## § 6 Summary and verdict

The project answered its first review fast and well: invariants in the fuzz walks, golden files, an ADR on the format of record, date rules compiled once, and an architecture test that reads compiled code. The biggest strength is still the method, now with a study plan that turns the owner's understanding into something tracked. The biggest new risk is small but sharp: **the quality gate is flaky**. Since `cb96d53`, the architecture test's calls to `:xref` warn at compile time on some runs, and `--warnings-as-errors` then fails `mix check` with every test green; the pre-push hook will reject good pushes at random, and a gate people learn to rerun stops being a gate. The biggest risk overall is unchanged: the command layer, which the web, custom keys and Wol all wait for, has not started. Fix the gate today, then start the command layer, and design its commands so that an agent with no cursor can call them.

## § 8 Architecture

**What is right.**

- **Caches travel in values** (ADR 0035). The date rules are compiled by a pure function (`DateParser.compile_rules/2`), put in `Core.Context` with a key that says what they were made for, and kept by the shell in `State.reader` (`lib/agendum/tui/state.ex:100`). A stale cache is missed, never used. **Joe** observed that this is the right shape: the core stays a function, and the speed comes from the value the caller holds, not from hidden state. Adding 100 dated items went from 92 to 13 ms. The same pattern is ready for the view cache.
- **The format of record is decided** (ADR 0034): the Erlang-term file stays for speed at volume (3,053 items: 53 KB, load 4 ms, against 1.5 MB and 27 ms in JSON), JSON is for people, and many users get a database. **Joe** accepted the decision because it comes with the golden files, which make every format change visible as a failing test rather than a surprise in someone's file.
- **The architecture rules are now read from compiled code** (`test/agendum/architecture_test.exs:8-31`), and a test proves an alias cannot hide a call (line 215).

**What worries the panel.**

1. **The command layer has not started**, and the count of core calls in `TUI.Update*` is 85, as it was this morning. **José** repeated that this is the change everything else waits for, and added a point from today's reading: the view's commands act on *the highlighted row*. `ViewKeys.run/3` passes `Layout.current_row(state)` to every command (`lib/agendum/tui/update/view_keys.ex:139`). A command in the core must name its target (an item id, a category id), or no web page and no agent can call it.
2. **Backward compatibility is not a promise yet** (ADR 0034). It is the honest choice with one user. **David** asked that the day of the promise be written down as a condition (the first outside user, or the first release), so that it is not decided under pressure.
3. **Undo lives in the TUI** (`lib/agendum/tui/history.ex`). For one person at a keyboard that is right. For an agent's batch of changes, or a web session, the core has no notion of "these changes belong together". The multi-user plan's command log was that notion; ADR 0034 moved storage towards a database, and the plan's § 3 is to be rewritten. The panel asked that the rewrite keep a place for grouping changes.

## § 10 Tests and verification

**What is right.**

- **The fuzz walks check meaning** (`572ef15`): after every random key, `Agendum.Core.Invariants.violations/1` checks the data model's invariants (the tree, symmetric links, exclusive families, R7c, one id space below `next_id` …) and undoing a key's steps must give the file back exactly. **Joe** called this the most valuable change of the day: crashes are loud, and these are the quiet bugs.
- **Golden files** (`1ae50ce`, `test/agendum/golden_files_test.exs`): a real version-33 file, written through the facade so that every field of every stored struct is set, with its facts beside it. Every later format must load it.

**What worries the panel.**

1. **The gate is flaky.** In this session, 3 of 8 runs (`mix check`, or `mix test --warnings-as-errors`) failed with all 1,659 tests passing: `:xref.start/1`, `add_directory/3` and `q/2` are "undefined" when the test file is compiled, because OTP's `tools` application is put on the code path only at run time, in `setup_all` (`test/agendum/architecture_test.exs:21-25`), and whether it is already there depends on the run. `--warnings-as-errors` turns the warning into a failure. A second warning came from the golden files' `.facts.exs`, which ExUnit took for misnamed tests; that one was fixed during the session (`028147b`). **José** suggested loading `tools` in `test/test_helper.exs` before any test file compiles, or `@compile {:no_warn_undefined, :xref}` in the test; either is a line. **Joe** added that the cost of a flaky gate is not the reruns, it is that people stop believing a red result.
2. **No CI yet**; the pre-push hook (`c0a5758`) is a good stand-in for one person, and it makes point 1 more urgent, not less.

## § 14 Agent readiness

**Claude** said: this is my item, so I will say plainly what I looked for. Could an agent, today, do one ordinary thing a person does (add an item, see where it was filed and why, read a view) without pressing keys? And could the person trust what it did?

**What is ready.**

- **The tools exist as pure functions.** `Agendum.Core` has 155 delegates (`lib/agendum/core.ex`), each taking a database and returning one: `add_item/4` (line 75), `assign/4`, `export_json/1`. Because the core is pure, an agent's change can be computed, inspected and thrown away before anything is written. I find this the most important property for agents, and it was built for other reasons.
- **Reading a view is a function.** `Agendum.Core.ViewModel.build/3` (`lib/agendum/core/view_model.ex:64`) turns a view into sections and rows as data: the natural answer to "show me what is due this week".
- **Proposing is already in the core.** `Core.questions/1` and `answer_question/4` (`lib/agendum/core.ex:143-144`, R16) are the path for suggested assignments that the person accepts or refuses. Wol's first principle, "the agent proposes; the person decides" (`docs/plans/WOL-IN-THE-MACHINE.md`), can use it as it is.
- **The repository is easy for an LLM to read.** `CLAUDE.md`, `docs/INDEX.md`, numbered rules and seven skills. This review is evidence of it. But that is the *developer's* agent; the user's agent needs a door into the program, not the repository.

**What is missing.**

1. **No door without a keyboard.** The CLI opens the TUI and nothing else (`lib/agendum/cli.ex:7-19`); there is no `add`, no `view`, no `export`, no JSON on standard output. An agent today would have to write Elixir against the facade, or drive keystrokes. **David** pointed out that `agendum add "text" FILE`, his capture item, is the same door.
2. **Commands act on a cursor.** The named commands in `Agendum.TUI.Commands` (names, summaries, counts) have exactly the shape of a tool list, but they run on the highlighted row (§ 8, point 1). A tool needs explicit arguments.
3. **No reasons.** `add_item/4` returns `{db, id}`; which category the item went to, and *why* (which word matched, which condition, which action), must be found by comparing databases. "Filed under Kanga because the text says Kanga" is what makes an agent's change explainable, and what makes Agenda's own automatic filing less mysterious to a new user. **Mitch** agreed strongly on the second point.
4. **No batch undo outside the TUI** (§ 8, point 3). An agent that files twenty items needs them taken back as one.
5. **Two writers, no warning.** `Store.save` writes a temporary file and renames it (`lib/agendum/store.ex:64`): safe against a crash, but the TUI does not notice that the file changed on disk since it was loaded. If `agendum add` or an agent writes while the TUI is open, the TUI's next save silently undoes it. **Joe** called this the first thing to fix once a second writer exists.
6. **A whole file does not fit in a model's context.** The golden file's 53 items are 123 KB of JSON (ADR 0034); 3,053 items are 1.5 MB. With ingested items, the agent must work through views and searches, not the export. That argues for view and search tools first.
7. **Item text is not yet treated as untrusted.** Ingested items (RSS, calendars; level 2 in `ITEM_LEVELS.md`) will be text written by strangers, read by a model that can change the file. The Wol plan's principles do not yet say that item text is data and never instructions. It should be principle 6 before the first feed is read.
8. **No golden tasks.** Wol's principle 4 (tested without a model) is right; there are no tasks yet: a small file, a request, the commands a good answer would propose. They can be written before any model is chosen, and they would also test the command layer's design.

**Claude** concluded: the core is a better home for an agent than most programs I am asked to work in, because it is pure and its rules are explicit. The distance is in the doors and the receipts: commands that take arguments, return what changed and why, and can be grouped and taken back. Those are the command layer's own goals, so the agent costs little extra if they are designed in now, and a great deal if added later.

## § 16 Points of disagreement

- **Agent first, or person first?** Claude would design the command layer's first commands as tools from the start (explicit targets, results with reasons). David would build `agendum add` first, for capture, and let the agent wait. They agreed that the same door serves both, and that `add` is the first command either would choose.
- **The binary file.** Carsten still prefers a text file people can read as the data's home; Joe accepts the binary with golden files and an exact JSON round trip; Mitch notes that the decision is ADR 0034's, made with the owner's reasons, and should be revisited only when other people keep data in Agendum.
- **The vision's breadth.** Mitch and David would narrow it until the "who it is for" paragraph exists. Claude sees the item levels as the most distinctive idea in the repository and would keep them, built later. Nobody proposed building them now.

## § 17 Resolutions

The meeting resolved to recommend:

1. **Make the gate deterministic**: load OTP's `tools` before the test files compile (`Mix.ensure_application!(:tools)` in `test/test_helper.exs`) or tell the compiler `:xref` is expected; then run `mix check` ten times in a row as the proof. *S · José, Joe*
2. **Start the command layer**, with each command taking explicit targets (ids, not the highlighted row) and returning what changed. Typed modes as each place moves (already planned). *L · José, Claude*
3. **`agendum add "text" FILE`** as the first command with no keyboard: filed by the core as if typed in the main view, printing where it was filed. It serves capture (David) and is the first agent tool (Claude). *S–M · David, Claude*
4. **Notice a file changed on disk** before saving over it (size and modification time, or a hash, kept at load): ask, as Agenda would ask about unsaved changes. Needed the day `add` exists. *S · Joe, David*
5. **Reasons with assignments**: let automatic assignment say why (matched word, condition, action, R-number) in its result, for the Questions box, for F1 on an assignment, and for an agent's report. *M · Mitch, Claude*
6. **Write who Agendum is for**, the placeholder at the top of `docs/VISION.md`, and make the vision and the roadmap agree on what comes first. *S · Mitch, David*
7. **Five real users**, with a date. *S to arrange · David, Mitch*
8. **Golden tasks for Wol**, before any model: a few small files, a request each, and the commands a good answer proposes; and a sixth principle in the Wol plan, that item text is data, never instructions. *S · Claude*
9. **The `.AG` importer**, still the feature that brings Agenda's old users. *M · Mitch, Carsten*
10. **The GTD starter**, as planned. *S · David*
11. **CI** when the repository is on GitHub, as planned. *S · José*
