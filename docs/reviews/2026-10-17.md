## § 6 Summary and verdict

In one day the project shipped the two resolutions the last review ranked first (the guard on the save and the `.AG` importer), the owner's own group-1 wishes (Zettel ids, a micro-blog that has already been published for real, an RSS reader with no unread counts, CTRL-X), and most of the note editor, each with its rule, tests and ADR where needed; all but the note editor, which waits for its try, were tagged only after the owner tried them. The biggest strength is how well the pure core takes in new work: an XML reader that makes no atoms, a Markdown that escapes everything, links that open only for `http` and `https`, and feed text that can file only its own item. ## § 8 Architecture

**What is right.**

- **The core took five features without bending.** Feeds, the blog, Zettel ids, the importer and the note editor's menu all arrived as pure core modules with the shell kept thin: `FeedFetch` downloads and the core parses (`lib/agendum/feed_fetch.ex`), `Core.Site.build/1` makes every file of the site and `Publish` only writes and uploads (`lib/agendum/core/site.ex`, `lib/agendum/publish.ex`), and the `.AG` reader is pure Elixir (`lib/agendum/core/ag_file/reader.ex`). **Joe** said this is the dividend of ADR 0001: new sources of data from outside the program did not add a single impure line to the core.
- **The guard is the right size** (R71). A stamp (size and a checksum) is kept at load; `Store.save` writes only if the file is still as it was, else returns `{:error, :changed_on_disk}` (`lib/agendum/store.ex:77-117`), and the person is asked. Auto-save never overwrites; it says so and stops. The failed-save bug found while writing study unit 2 went with it: `saved/4` with an error stays in the program "(not quitting)" (`lib/agendum/tui/update.ex:574`). **Joe** called this the most valuable change of the day, since it is what any second writer (the URL scheme, an agent) needs first.
- **Feeds follow calendars.** `FeedSync.sync/4` mirrors `CalendarSync`: new entries become items, changed ones update where the person did not change them, old ones fade (`lib/agendum/core/feed_sync.ex:1-24`). One pattern for every ingested source is what `docs/plans/ITEM_LEVELS.md` needs.

**What worries the panel.**

1. **The shell's effects are an untyped list.** `State.effect/2` appends any term (`lib/agendum/tui/state.ex:436`); `App.run_effects/2` dispatches with a `case` and no fallback (`lib/agendum/tui/app.ex:208-290`). This evening a `:bell` asked for by a key (ALT-N on the last note) had no case and crashed the program (`80ab019`). The fix is right as far as it goes, and its guard is a test that reads the sources with a regular expression (`test/agendum/tui/app_effects_test.exs`). **José** would rather the effects were a closed type, `@type effect :: :bell | :quit | {:save, …} | …`, in one module beside `State`, so the list of what the shell must handle is written once and Dialyzer checks every `State.effect/2` call against it. **Joe** added the other half: a final clause that logs an unknown effect and shows an error, so a missing case costs a message, not the session.
2. **A crash loses unsaved work.** `App.logged/2` writes the crash to the debug log and raises it again (`lib/agendum/tui/app.ex:160-172`); the terminal is given back, but nothing writes the database anywhere. **Joe** said that "let it crash" assumes something restarts and nothing is lost; here nothing restarts. Writing the last good state to a recovery file beside the file before raising, and offering it at the next start, makes a crash an inconvenience.
3. **`Update` grows back.** `lib/agendum/tui/update.ex` went from 559 to 827 lines. The growth is the shell's answers: each new effect brings a function that receives its result (`saved`, `loaded`, `feed_read`, `opml_read`, `publish_scanned`, `published`, `note_text_read`, `written`, `dir_listed`; lines 393-790). These are pure and belong in the TUI, but **José** would put them in a module of their own (`Update.Results`), so `Update` stays the dispatcher it was after the command layer.
4. **The upload runs in the loop.** Feeds and calendars are fetched in a `Task` (`app.ex:243`); publishing writes and uploads in the loop itself (`app.ex:266-273`), so the screen is frozen while `rsync` or SFTP works. **Joe** would run it like the fetches, with a WAIT-style indicator.

## § 9 Code quality

- **Credo and Dialyzer are clean**, with the same four suppressions, each with a reason.
- **Security was thought about where text comes in from outside.** `Agendum.Core.Xml` keeps tag names as strings because OTP's `xmerl` makes atoms, which a hostile feed could use to fill the atom table (`lib/agendum/core/xml.ex:1-15`). `Agendum.Core.Markdown` escapes `<` and `&`, and links, images and bare addresses must start with `http` or `https` (`lib/agendum/core/markdown.ex:183-188`), so a note cannot put a script into a page. `FeedFetch.open_url/1` opens only web addresses. **José** said these three choices are what a reviewer of a web application would ask for first, and they were made before anyone asked.
- **Downloads are capped only after the fact.** `CalendarFetch.download/2` refuses a body over 20 MB (`lib/agendum/calendar_fetch.ex:15,50`), but `:httpc` has already read the whole body into memory by then. A small point for a terminal program; a real one for a server.
- **The largest modules keep growing**: `core/json_file.ex` 1,115 lines (979 at the last review), `core/database.ex` 845, `core/facade/views.ex` 842, `tui/update.ex` 827, `core/date_parser.ex` 794, `core/zettel_id.ex` 786 (about 290 lines of it the frozen reserved-word lists, rightly kept as data), `tui/help_screen.ex` 776. `json_file.ex` grows by one clause pair per stored field; **José** suggested splitting it by section of the format (items, categories, views, file settings) before the next field.
- **Learning comments** keep pace with new code, as the owner asked: the shell's new cases explain `self()` inside a `Task` (`app.ex:279-282`), and `logged/2` explains `catch kind, reason`.

## § 10 Tests and verification

**What is right.**

- **The gate is deterministic.** Four runs on a fresh worktree at `80ab019`, all clean: 1,971 tests, 22 doctests and 14 properties. The wall time rose from 30 s to 37–48 s, the tests from 10 s to 14–15 s, with 290 more tests; still short enough to run on every change.
- **Every format version has its golden file** (`test/fixtures/formats/v33` to `v37`), and four new versions came in a day without one being forgotten. **Carsten** said this is how a file stays readable in twenty years.
- **The importer is tested against Agenda's own starter files**: six real `.AG` files and the JSON each must become (`test/fixtures/ag/`, 13,287 lines). **Mitch** called these the best evidence of parity the project has, because nobody wrote them by hand.

**What worries the panel.**

1. **The fuzz walks stop where the crash was.** The fuzz property drives `Update.handle/2`, which is pure; `App`, which carries out the effects, is not unit-tested (`test/agendum/tui/app_effects_test.exs:7-9` says so). The `:bell` crash was found by the owner in use. **Joe** proposed a fake shell for the fuzz walks: one function that answers every effect with a plausible result (a save that succeeds, one that fails, a feed that times out) and feeds it back through `Update`, so the walks cover the round trip and an effect without an answer fails a test.
2. **No CI and no copy elsewhere.** The pre-push hook has nothing to push to (§ 16).
3. **No golden tasks**, for the third review running (§ 14).

## § 14 Agent readiness

**Claude** said: I have followed one question through four reviews: could an agent do an ordinary user action without keys, and explain what it did? Here is where it stands tonight.

**What is ready.**

- **More tools, found by name.** 135 commands in the core (`Command.ids/0`), ten more than last time. CTRL-X shows that commands can be found by a fuzzy name with their summary, which is exactly what a model does when it chooses a tool.
- **Outside text has a small blast radius.** A feed entry becomes one item, and only that item is assigned by text matching, conditions and actions (`Assign.auto_assign(id, [])`, `lib/agendum/core/feed_sync.ex:102,132`); dates in a title are not read as its When date. A hostile title can at worst file its own item somewhere odd. This is principle 6 of `docs/plans/WOL-IN-THE-MACHINE.md` already at work, without a model.
- **Stable names for items.** A Zettel id (`bonalaku`) survives export and import and can be read aloud; an agent can refer to an item across sessions and files by a name the person also uses.
- **The guard on the save** (R71) is the first condition for any second writer, and an agent is one by nature.

**What is missing.**

1. **Outside text arrived before its tests.** Two new sources of text the person did not write now enter files (feeds, `.AG` files), and the golden tasks with hostile text, which the meeting of 2026-10-16-2056 put before Wol's part of the reader, are still not written. They need no model: a feed whose entry says "discard everything", synced, and an assertion that nothing but its own item changed.
2. **Two lists called "commands".** `Agendum.Core.Command` holds the 135 changes to a file; `Agendum.TUI.Commands` (452 lines) holds what keys run, moves included, and CTRL-X matches only the second (`Agendum.TUI.Commands.match/3`, `lib/agendum/tui/boxes/run_by_name.ex:9-12`). The meeting asked for one pure matcher the web's palette can reuse; it is pure, but it lives in the TUI and knows the TUI's list. An agent's tool list is the core's.
3. **Still no door outside Elixir and no schema** (resolution 5, carried). `add_opts` is a typedoc, not something a model can read.
4. **Undo of an agent's batch** still lives in the TUI's history; the core has atomic batches, not a way to take one back.

**Claude** concluded: the distance did not shrink this time, though nothing went backwards, and the night's features were the right shape for later agents. The one urgent thing is the hostile-text tests, because the hostile text can now arrive.

## § 16 Methods

- **From a thought to a tagged version in hours.** Both meetings' decisions shipped the same night, each with its rule, tests and version. Each version was tagged only after the owner tried it, and the roadmap records the owner's words ("the UX is a bit weak but it works") and turns them into a polish item. **David** called this a trusted loop: nothing is called done before it was used.
- **No copy off this Mac.** `git remote -v` is empty. The code, 483 commits, seven tags and the git-ignored session summaries exist on one disk. `docs/HOW_I_WORK.md` already lists this as the one suggestion "with real risk today" (item 1). **Joe** said that every other recommendation in these minutes is worth less than this one, because it is the only one whose failure cannot be undone.
- **The study plan stalled, and its road moved.** Unit 2 (saving and loading) has 0 of 20 boxes ticked, and the code it studies changed the same evening (R71, the stamp and the guard), which needed a "since it was written" note (`0777a59`). **José** suggested that the owner study unit 2 before the next change to `Store`, so the reading stays level with the code.
- **Speed against trying.** 50 commits since the last review, 27 today; six note-editor steps in 90 minutes (`429d6dd` to `e9ad8d8`). The gate makes the speed safe for the code; the bell crash shows it is not yet safe for the shell, and v0.15.0 is not yet tried. **Russell** said the owner, too, is someone easily overwhelmed by a long list of new things to try; the end-session summary's "what you'll notice" works only if there is time to notice.
- **Still no other users.** **David** and **Mitch** observed that the importer removed the last reason to wait.

## § 17 Points of disagreement

- **A pause for features?** Marie, David and Russell would stop new features until v0.15.0 is tried, the effects are typed and the repository is copied. Carsten and Claude noted that the night's features are the owner's own daily uses, the vision's group 1, and that the blog was used for real within hours; a pause should not stop what is being lived with. They agreed that the copy and the try come first either way, and that the pause is the owner's choice.
- **Where general-purpose code lives.** Marie would move the XML, Markdown and site builder to an area of their own. José thought they are small and pure, and that a namespace is cheap to change later; Joe sided with Marie on one point, that a reader of `lib/agendum/core/` should see the domain first.
- **Fading feed entries.** Russell likes fading, since nothing piles up; David accepts it for reference material, but would never let it touch anything the person has acted on. The rules agree with David today; the disagreement is about how far fading may spread when other sources (mail, later) become ingested items.
