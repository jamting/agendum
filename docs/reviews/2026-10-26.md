## § 6 Summary and verdict

The truthful clone is done, and it was done carefully: in five days the project built View Properties, recurring items on every date, Agenda's menus, boxes, messages and key bars, a file password with real encryption, a trash and Agenda's help with 107 topics, and checked the menus, boxes, messages and key bars against captures from the real Agenda in DOSBox, so that "like Agenda" is now a test and not an impression. The biggest strength is that this speed did not cost the foundations: every push went through the gate, the nightly long fuzz run stayed green, and the extras moved to their own shelf behind an `:xref` rule before a single one was hidden. The biggest risk is in the owner's own file, not the code: 13,184 feed entries that have faded from view still keep their full text in the file, three quarters of its 17 MB, and that is why a save takes half a second and the debug log shows its first slow answers in real use. The roadmap said to wait for exactly this evidence before building a view cache; the evidence has come, and it points to the data, not the view. The one thing to do next, before the public repository: let the faded entries keep only their ids, and finish the clone's two remaining safety items (the recovery file and the hostile-text tests), with the logger bug that can print over the screen.

## § 8 Architecture

**José** read the extras' shelf against ADR 0044. It is what the last minutes asked for: the core's extras in `lib/agendum/core/extras/` (thirteen modules, from `blog.ex` to `zettel_links.ex`), the shell's in `lib/agendum/extras/`, and an architecture test that names the shelf, the extras' homes outside the core and the faithful modules allowed to name them (`test/agendum/architecture_test.exs:209-222`). The exceptions were written before the move (`6eb6455`), so the rule was strict from its first day. He called this the best-executed structural change in the project so far.

**Joe** found the shell safer. The effects are a closed list with a type (`lib/agendum/tui/effect.ex`), every clause of `App.perform/2` is one shape, and an unknown effect goes to the log and is skipped instead of crashing (`lib/agendum/tui/app.ex:343-350`). That closes the crash of 2026-10-17 for good.

He then raised what the logs showed. Every effect runs in the main loop, one after another (`lib/agendum/tui/app.ex:221-242`), so a save is a pause in which no key is read. On the owner's file a save took 548 to 557 ms, and an auto-save 1,075 ms (session log of 2026-10-26, 11:19 to 11:54). Measured on a copy in the scratchpad: 483 ms for the whole save, of which 460 ms is `:erlang.term_to_binary(db, [:compressed])` (`lib/agendum/store.ex:109`); without compression it takes 9 ms, at compression level 1 it takes 134 ms. He said the order of work is plain: first make the data smaller (§ 15), then consider a lighter compression level, and only then think about saving in a task. Saving in the background brings back the question of what happens to keys typed during the save, which the present design answers simply by not having it.

**José** returned to `Update`. It is now 987 lines (842 at the last review), and lines 479 to 934 are the shell's answers (`calendar_read`, `feed_read`, `saved`, `loaded`, `imported`, `published`, `trashed`, `copied` …): the half of the module that is not a dispatcher. This is the fourth review to say so. He asked the owner either to do it (a module such as `Update.Results`, no change in behaviour, one commit) or to say plainly that it is not worth doing, so that the item stops being carried.

**Joe** added one more thing the logs and the roadmap agree on: Erlang's logger can print over the screen (ROADMAP, Fixes and polish; the owner saw it on 2026-10-25). The default logger handler writes to standard output, which in raw mode is the drawn screen. While the TUI runs, the logger belongs in the debug log. It is small, and an old user who sees error text across their Agenda would not come back.

## § 11 Helpfulness to users

**David** found his request of the last review answered: a recurring item now shows on every date it recurs, in datebook slots and in views with a When range (SPEC R14a), so a weekly meeting is in next week's datebook. For a person who is easily overwhelmed, a pause after CTRL-S with no sign of what is happening is the kind of small friction that adds up to "this tool is unreliable". Making the save quick is better than adding a "Saving…" message, but if a save will ever take longer than a moment, the screen should say so.

## § 14 Agent readiness

**Claude** said: the thaw on 2026-10-26 means my lens can move again, and the project is closer than the "headless entry points" row suggests.

1. **There is a headless reader, and I use it.** `mix agendum.thoughts` reads the owner's own file and prints the thoughts for the next meeting as Markdown, without a terminal or a keystroke (`lib/mix/tasks/agendum.thoughts.ex`). The `meeting` skill depends on it. That is the first routine use of an Agendum file by an agent, and it works. It is a development task, not part of the escript, and it only reads; but its shape (a file in, Markdown out, nothing changed) is the shape a first public headless command should have: `agendum --json view NAME FILE`, read-only, in the escript.
2. **Commands, and their help, are ready to be tools.** 151 core commands run through `Core.Command.run/3` (`lib/agendum/core/command.ex:437`), and 107 help topics are plain text files (`lib/agendum/tui/help/topics/`). An agent could explain a box from the same text the person reads. The matcher (`lib/agendum/tui/commands.ex:534`) is still in the TUI, and commands still have no schema for their arguments.
3. **The debug log keeps secrets.** Effects without a clause of their own are written with `inspect` (`lib/agendum/tui/debug_log.ex:182`), so every `{:fetch_feed, id, url}` and `{:fetch_calendar, id, url}` puts the full address in the log. Today's logs hold feed addresses with private tokens in them, of the kind a calendar or a saved-items feed uses to stand in for a login. The same file was careful elsewhere: passwords are hidden (`debug_log.ex:139-142`, `:177-178`). Before any outside user is asked to send a log, and before any agent reads one, the URLs should be logged without their query string (or as the feed's name).
4. **Hostile text is still untested**, and still clone work: a `.AG` file or a feed whose item text asks for changes must import as plain items and only its own (ROADMAP, The clone's safety). Feed text is the first outside text an agent would read (`docs/plans/WOL-IN-THE-MACHINE.md`, principle 6).

**José** asked whether golden tasks should now start. I think they should, in a small way: three files, three requests, the commands a good answer runs, checked against `Core.Command.run/3`. They test the command layer's design whether or not a model ever runs them. **Joe** agreed, after the safety items.

## § 15 Tidiness and scope

**Marie** looked by category.

**What is in its place.**

- **Plans.** Every plan in `docs/plans/` has a status line; the finished ones are in `docs/plans/archive/` (seven); AGENDA_PARITY became a record the day the clone was done, as she asked on 2026-10-26.
- **The roadmap** shrank from 58 open boxes to 40, with an "In order" list at the top that names the next two things and admits that the third is the owner's choice.

**What could be kept less, or put in its place.**

1. **The faded feed entries.** This is the largest thing she has found in any review. The owner's file has 243 feeds and 14,423 entry snapshots; 13,184 of them have faded or been discarded (`item: nil`), and each still keeps its title, note and link (`lib/agendum/core/extras/feed.ex:22-28`). They take 12.7 MB of the file's 17.0 MB as a term; the notes alone are 10.2 MB. Their only remaining job is to stop a refresh from bringing them back, and for that the entry's id is enough (with its publish date, if `keep_days` needs it to forget the id once the feed no longer lists the entry). Keeping them costs half a second on every save, 5.3 MB on disk and in every backup, and, in the JSON export, a document no person or model would want to read. She advised keeping the id and letting the rest go; it is a format change, so it needs a version, a golden file and a line in `docs/JSON_FORMAT.md`.
2. **SPEC is becoming a diary.** It grew from 135 KB to 183 KB in five days. Its longest rule, R80, is one line of 6,169 characters, and 75 places say when something was checked in Agenda or chosen by the owner. That provenance is valuable, but its home is `ROADMAP_DONE.md`, the ADRs and the summaries; a rule should say what is true. She suggested slimming a rule when it is next touched, not in one sweep (§ 17).
3. **Two stale texts.** `docs/VISION.md` (§ 13), and the parity plan's modifications list, which says "three differences remain" in boxes and lists one (`docs/plans/AGENDA_PARITY.md:147`). A `tidy-docs` pass before the public repository would find these and their cousins.
4. **Five logs are not enough to judge from.** The debug log keeps five sessions (`lib/agendum/tui/debug_log.ex:31`); all five are from today. The panel could not see whether the slow answers began this week or earlier. Ten or a week's worth would cost little.

She said, as always, that she advises and the owner decides, and that the session summaries, kept complete by the owner's choice, were not on her list.

## § 17 Points of disagreement

1. **Provenance in SPEC.** **Marie** would keep SPEC to the rule and move "checked in Agenda 2.0, 2026-10-25" and "the owner's choice" to the done list and the summaries. **Carsten** and **Mitch** would keep them where they are: when a rule says "as Agenda's (checked …)", a reader knows it is not a guess, and that is what makes the clone truthful. **Claude** noted that a model reading SPEC pays for every word, but also uses the provenance to decide whether a behaviour may change. The panel agreed on a middle way: keep a short "(checked in Agenda)" on the rule, and move the longer stories of how and when to the done list. The owner decides.
2. **Where the feeds' bulk belongs.** **Joe** wants the simplest fix: ids only for faded entries, nothing else changed. **Carsten** sees a larger question behind it: ingested items (`docs/plans/ITEM_LEVELS.md`) may not belong in the person's file at all, and a separate store for them would keep the file small whatever the feeds do. Both agreed that the simple fix comes first and does not prevent the larger one.
3. **What comes after the public repository.** **Mitch** would look for users; **Claude** would start golden tasks and a read-only headless command; **David** would build the GTD starter; **Russell** the gentler starter for the easily overwhelmed. Each serves a different group in `docs/VISION.md`. The panel does not vote, and the owner chooses (ROADMAP, In order 3).
4. **The pace.** **Russell** and **David** would slow down now; **José** pointed out that the gate held at full speed and that momentum has value too. They agreed that the next few days are for using the clone rather than adding to it.

## § 18 Resolutions

The meeting resolved to recommend:

1. **Let the faded feed entries keep only their ids.** A faded or discarded entry keeps its id (and its publish date if `keep_days` needs it), not its title, note and link; a format version with its golden file and JSON schema. On the owner's file this frees about 12.7 MB of 17.0 MB and should bring a save from ~480 ms to well under 100 ms; measure before and after on a copy. Then consider compression level 1 (`lib/agendum/store.ex:109`: 460 → 134 ms on today's file). _S–M · Marie, Joe_
2. **Finish the clone's safety before the public repository**: the recovery file on a crash, the hostile-text tests for `.AG` files and feeds, and the logger sent to the debug log while the TUI runs (ROADMAP, Fixes and polish). An old user's first crash or garbled screen costs more than any missing command. _S–M · Joe, Claude_
3. **No private addresses in the debug log.** Log feed and calendar fetches by name or by host, without the query string (`lib/agendum/tui/debug_log.ex:182`), and keep more than five sessions (a week, or ten). Needed before anyone else is asked to send a log. _S · Claude, Carsten_
4. **Keep the long fuzz run's output**, locally in a file and in CI as an artifact on failure, so a failure can always be repeated. _S · Joe_
5. **A tidy pass and a dry run before the public repository**: `tidy-docs` for the stale texts (VISION's freeze paragraph, AGENDA_PARITY's "three differences"), then the `git filter-repo` copy built and checked by `mix check` before anything is pushed. _S–M · Marie, José_
6. **A few days of use, nothing new**: the owner on the clone and their own file, and the session summaries noting, for each version, whether the owner tried it. The next work then comes from use. _S · Russell, David_
