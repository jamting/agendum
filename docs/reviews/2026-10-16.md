# Expert panel review, 2026-10-16

The first review of Wol's Agendum, at commit `c3c416e` (version 0.5.0), eight days after the first commit. The panel is five lenses: **José Who Brews** (Elixir), **Great-Uncle Joe** (Erlang/OTP), **Carsten Stargazer** (Org-mode), **Old Mitch Lilypad** (Lotus Agenda) and **David the Squirrel** (GTD). The voices are perspectives in the spirit of these people's public work, written by Claude; they are not their words. Made with the `expert-review` skill.

## Summary

Agendum is an unusually disciplined project for its age. A pure core, an Elm-style UI, effects as data, and architecture rules enforced by tests give it a base that most hobby projects never reach, and `mix check` passes clean (1,629 tests in 12 seconds, no Credo or Dialyzer issues). The biggest strength is the method: numbered rules, ADRs, test-first work, and the real Agenda running headless as an oracle. The biggest risk is direction, not code: the roadmap pushes towards 100% surface parity with a 1988 program whose learning curve is what limited it, while the work that would unlock everything else (a command layer that takes user actions out of `TUI.Update`) is still open. Second risk: the system has had one user. The next thing to do is finish the command layer, then put Agendum in front of five real people, starting with those who still miss Agenda (an `.AG` importer brings them).

## Architecture

**What is right.**

- **Functional core, imperative shell, for real.** `Agendum.Core` and everything under `lib/agendum/core/` is pure; the clock comes in from outside (`TUI.App` calls `Update.tick/2`), and the architecture test fails on clock, file, process or random calls in the core (`test/agendum/architecture_test.exs:27`). **Joe:** this is the shape I would want: the hard part is plain functions over values, and the only process that matters is the loop that reads keys.
- **Effects as data.** `Update.handle/2` returns `{state, effects}`; the shell runs `{:save, path}` and friends (`lib/agendum/tui/update.ex:14`). Every UI behaviour is testable with key sequences and no terminal.
- **The data model follows the patent.** Links are stored, membership is computed (ADR 0004, `Agendum.Core.Assign`), one id space for every object. Deleting a category is "drop its links" and nothing more.
- **No runtime dependencies and an own terminal layer** on OTP 28 raw mode (ADR 0002, 0021). The escript is one file with nothing to install. **José:** an honest trade: you own the key decoding and the diffing screen, but nothing upstream can break you.
- **A facade with area modules** (ADR 0023): 155 delegates in `lib/agendum/core.ex`, written in `core/facade/*`. A second front end has one place to look.

**What worries the panel.**

1. **A user action is still defined in the UI.** `TUI.Update` and its modules make 85 direct calls into the core, and several keys run a sequence of facade calls plus logic of their own (the alarm prompt in `lib/agendum/tui/update/prompts.ex` works out the alarm's time). The web plan names this the largest gap itself. Until a command layer exists, a web front end, customizable keys, a "modern mode" and Wol all have to re-assemble actions from keystrokes. **José:** this is the one structural change that every plan on the roadmap waits for. The keymaps and named commands (R65, ADR 0033) were the first half; the second half is a command *the core* applies.
2. **The file format is the in-memory struct.** `Agendum.Store` writes `:erlang.term_to_binary` of `%Database{}` (`lib/agendum/store.ex:10`), and every new field bumps the version: 33 versions in 8 days, each with an upgrade path. It is safe (`:safe` decoding, atomic rename) and it works, but it ties years of people's data to today's module and field names, which the `Agenda.*` → `Agendum.*` rename already had to patch around. **Joe:** a file format is a protocol; protocols should be written down and boring. You already have one written down: the JSON schema (`docs/JSON_FORMAT.md`), with a round-trip property. Decide which one is the format of record before the web plan adds a third (a command log).
3. **UI modes are untyped maps.** `State.modes` is `[map]` (`lib/agendum/tui/state.ex:39`), with about fifty kinds told apart by `%{type: …}`. Dialyzer cannot see a misspelt key in a mode, and the fuzz test is what catches it. **José:** a struct per mode (or per box, as `Boxes.Box` already half does) makes the compiler do that job, and documents each mode's fields where it is defined.
4. **Performance is designed around, not yet measured as a budget.** Every key rebuilds the view, and reading a date compiles about 100 regexes each time (`lib/agendum/core/date_parser.ex:68`, ROADMAP "To look into": Execute over 300 dated items takes ~1.1 s; a cursor move at 3,000 items ~145 ms). **Joe:** make it work, make it beautiful, then make it fast; you are at the third step for dates. The compiled rules belong in `Core.Context`, which is built once; it keeps the core pure and costs one field.

**Undo by snapshots** (ADR 0005, 100 steps, `lib/agendum/tui/history.ex:16`) is right for one person: on the BEAM a snapshot shares almost all its structure with the previous one. It is not the model for shared files; the multi-user plan already says so.

## Code quality

- **The gate is real and clean.** Format, warnings as errors, Credo, Dialyzer and tests in one command (ADR 0012); this run: no issues, all pass. Five Credo suppressions, each with its reason inline.
- **Idiomatic, small functions.** Pattern matching, `with` chains, pipelines, `@spec` on public core functions, `@moduledoc` everywhere. `Assign.do_assign/4` (`lib/agendum/core/assign.ex:44`) reads like the rule it implements, with the patent claim it follows named in the module doc.
- **Learning comments** explain Elixir idioms for an owner new to the language (`lib/agendum/core.ex:23`). **José:** unusual in production code and right here: the code is the owner's textbook. Keep each one about the idiom, not a retelling of the line, so they age well.
- **Large modules.** `core/json_file.ex` (979 lines), `core/facade/views.ex` (840), `core/database.ex` (801), `core/date_parser.ex` (759), `tui/help_screen.ex` (741), `tui/update/view_keys.ex` (721). None is out of hand; `views.ex` and `view_keys.ex` are the ones to split when the command layer moves logic.
- **The architecture test is a regex** (`test/agendum/architecture_test.exs:9`). It catches the ordinary mistakes, but an alias (`alias …Database, as: DB`) or `put_in(state.db…)` passes it. **José:** a compile tracer or `mix xref` on the call graph turns a convention into a guarantee.
- **Root clutter**, harmless but noticeable: `erl_crash.dump`, personal `.agendum` files and the built binary sit in the project root (all git ignored).

## Tests and verification

- **Tests at the level users experience.** TUI tests press keys and read the screen (`test/agendum/tui/copy_item_test.exs`), core tests use fixtures; tests are named after behaviour and rule numbers. 1,629 run in 12 seconds because modules run async.
- **Fuzzing the UI** (`test/agendum/tui/fuzz_test.exs`): random key sequences on varied screen sizes and files must never crash and every frame must fill the screen; a longer run is part of the workflow after big TUI changes. **The JSON round trip** is a property over files made by random keys (`test/agendum/core/json_round_trip_test.exs`).
- **The real Agenda as an oracle.** `tools/agformat/agenda_driver.py` runs Agenda 2.0 headless in DOSBox, so "what does Agenda do" is settled by experiment, not memory. **Mitch:** that is how you clone a product honestly.

**Gaps.**

1. **The fuzz property checks shape, not meaning.** It asserts no crash and frame geometry. The same random walks could check the data model's invariants after every key: no item directly in a category and its ancestor (R7c), at most one child of an exclusive parent, links and their reverse agree, every id below `next_id`, undo back to the start gives the starting file. **Joe:** invariants are where the bugs that lose data hide; crashes are the friendly ones.
2. **Format upgrades are tested on synthesized old files.** The store tests build a "version 6 file" by deleting fields from today's struct (`test/agendum/store_test.exs:87`). Real old files may differ in ways the test author did not think of. Commit a small golden file for each format version when it is made, and load them all in one test.
3. **No CI.** The gate runs only where someone remembers to run it; the GitHub plan has it but it is not done.

## Helpfulness to users

**David:** a system is trusted when it captures everything, you know where everything is, and you look at it regularly. Agendum is strong on the middle part and weak at both ends.

- **Capture and clarify: strong.** Typing free text and having it filed by names and dates in it ("Call Anna Lasky next Friday") is Agenda's gift and it works here, in English and Swedish, with confirmation of suggested assignments (R16) for those who want control.
- **Organize: strong.** Categories as contexts (@Calls, @Office), projects as parents, exclusive families for status (Next / Waiting / Someday), date filters and datebooks: everything GTD needs is expressible. Nothing makes it *obvious*: there is a Planner starter, not a GTD one.
- **Capture everywhere: missing.** Capture happens only at a terminal with the file open. There is no inbox file, no command-line `agendum add "…"`, no mail or phone path. Ideas arrive away from the desk. **David:** an open loop you cannot capture on the spot stays in your head.
- **Reflect: missing.** No support for the weekly review: items not touched for N days, projects without a next action, waiting-for older than a week. Agenda's views and conditions can build some of this; a starter could show how.
- **Trust in the data: good.** Atomic saves, auto-save (R54), undo, a debug log for crashes. Agenda's "Make backup on open" is still on the parity list.

**Carsten:** the people who stay with a tool for twenty years care about three things: their keystrokes, their text, and the ability to bend the tool. Agendum honours the first (Agenda's keys, keymaps, macros, count prefixes). The second is weaker: the file is an opaque binary; no `grep`, no `diff`, no editing in another program, no sync through git. JSON export helps, but it is an export, not a home. The third is coming (custom bindings, the command layer); a command layer is also what makes a scripting or plug-in story possible later.

**Mitch:** Agenda's learning curve is why it sold 200,000 copies and not two million (`docs/AGENDA_HISTORY.md`). Agendum reproduces it faithfully. The guide (Piglet) and the manual (Owl teaching Rabbit), the F1 help with greyed commands and reasons (R65a–c), and the starters lower it; "Modern by default" on the roadmap would lower it most, and is not started.

## Vision

The stated vision is three layers: a faithful Agenda (Milestone 2, ~80%), then beyond Agenda (flashcards, a micro-blog, Zettelkasten links, Signal alarms, more languages), then many users on the web, with Wol as an idea.

**Mitch:** the first layer is lovingly done and the parity document (`docs/plans/AGENDA_PARITY.md`) is a model of how to clone with intent: accepted enhancements and modifications are listed, everything else is a gap. But parity is measured on the surface (indicators, menu entries, File ▸ Abandon, Show Circular). The *essence* (capture, automatic filing, editable views, rules) is already there. The last 20% of surface will cost as much as the first 80% and few people will notice it. Agenda's real lesson is that its idea outlived its interface.

**David:** the "beyond Agenda" list reads as a set of the owner's interests (flashcards, blogging, Zettelkasten) more than a picture of the user's day. Each is reasonable; together they spread a tool whose promise is focus. Pick the ones that serve the trusted-system loop (capture, review) first.

**Both:** the vision would be stronger written as *who* Agendum is for, in one paragraph, at the top of the roadmap. Today it says what Agendum resembles.

## Methods

- **A specification as numbered rules** (R1 … R65), each with tests named after it and an index checked by a test; **ADRs** for decisions (33); **habit changes settled before code** (CLAUDE.md, workflow step 0); **one feature per commit**; the docs index, rule index and screens list checked by tests. **José:** this is more process than most companies manage, and it is what lets an AI pair work fast without making a mess.
- **AI-paired development at high speed.** 351 of 362 commits were co-authored with Claude, 35,000 lines in eight days, up to 90 commits a day. The guard rails (gate, architecture tests, fuzzing, oracle) are what make that speed safe. **Joe:** speed is not the risk; not understanding what you have is. The owner is new to Elixir; the learning-comments skill and the session summaries are the right answers. Reading one core module a week, by hand, would be a good habit.
- **Documentation volume.** ~6,900 lines of design documents and 1,643 of spec beside 35,000 of code, plus a guide and a manual. They are well kept (the `tidy-docs` skill, index tests), but every feature now touches four to six documents. Watch the ratio; a fact in two places is a bug waiting.
- **Feedback from use.** Every decision so far is the owner's, checked against the real Agenda. No other person has used Agendum. **David:** the system that works for its maker and the system that works for others are different systems; the earlier you see the second, the cheaper it is.
- **Format churn as a symptom.** 33 file-format versions in a week shows features landing one stored field at a time. Fine while there is one user with throwaway files; costly once anyone keeps real data.

## Where the panel disagrees

- **Parity first, or essence first?** Mitch and David would stop surface parity at "good enough" and spend the time on onboarding, capture and review. Carsten defends parity for the existing Agenda users: a tool for power users must not surprise their fingers, and they are the first customers. The `.AG` importer is where both views meet: it serves the old users and costs little now that the format is mapped.
- **Binary file or text file?** Joe is content with Erlang terms as a private format if JSON is the format of record. Carsten wants a text format people can read and diff as the *home* of the data. José notes that the web plan will store data its own way anyway, so the decision is about the terminal user's trust.
- **The TUI's own terminal layer.** José respects it; Joe would have done the same; Mitch asks whether every hour on key decoding is an hour not spent on the web front end where most future users are.

## Recommendations

1. **Finish the command layer** (ROADMAP, Towards many users): one named command per user action, applied by the core; `TUI.Update` only maps keys to commands, with an architecture test that keeps it so. It unblocks the web, custom keys, a modern mode and Wol. *L · José, Mitch*
2. **Check meaning in the fuzz walks**: assert the data model's invariants after every key, and that undo back to the start gives the starting file. *S · Joe*
3. **CI on every push** (GitHub Actions running `mix check`), as the GitHub plan says; it is an hour's work and protects everything else. *S · José*
4. **The `.AG` importer**: the format is mapped; reading a real Agenda file is the one feature that brings existing Agenda users, the natural first testers. *M · Mitch, Carsten*
5. **Five real users** before the next milestone: old Agenda users and keyboard-tool people, with the debug log on and a short interview each. *S to arrange · David, Mitch*
6. **Decide the format of record** (an ADR): JSON (or a future command log) as the long-lived format, the binary as a fast cache; and golden files for each format version in the tests. *M · Joe, Carsten*
7. **Compile the date rules once**, carried in `Core.Context`; then measure a view cache against the debug log's slow answers. *S–M · Joe*
8. **A GTD starter** (like the Planner): Inbox, Next Actions by context, Projects, Waiting For, Someday/Maybe, and views for a weekly review (untouched items, projects without a next action). It shows what the rules can do in a language many people already know. *S · David*
9. **Capture from outside**: `agendum add "text" file.agendum` from the shell (core does the filing, as typed in the view); later a mail or phone path. *S–M · David, Carsten*
10. **Typed modes**: a struct per UI mode, so Dialyzer and the compiler catch what the fuzz test catches today. Best done while the command layer moves things. *M · José*
11. **Write who Agendum is for** at the top of the roadmap, and weigh the "beyond Agenda" items against it. *S · Mitch, David*
