## § 6 Summary and verdict

The command layer, the change everything was waiting for, is done: every change to a file is now one of 125 named commands that take ids, are checked before they run, and return what changed, and the TUI's own logic shrank from 85 core calls to 19. The gate is deterministic again, the vision says who Agendum is for, and the first meeting on the owner's own agenda turned four ideas into shipped features in an afternoon. The biggest strength is now the core's shape: a front end, a test or an agent can drive Agendum entirely through data. The biggest risk has moved from the code to the world outside it: there are still no other users, no second door into a file, and no guard against two writers, and the feature that would bring the first users (the `.AG` importer) is on its third review without a start. The one thing to do next: guard the save against a file changed on disk, then build the importer, and put the five users' first sessions in the calendar.

## § 8 Architecture

**What is right.**

- **The command layer is the right shape.** A command is data, `{:mark_done, [42, 43]}`, and names its targets by id, never the highlighted row (`lib/agendum/core/command.ex:1-16`). `run/3` checks each argument's kind against the file before running (`:item`, `:category`, `:view` …, lines 410-425), so a stale id gets a reason, not a crash, and returns the new database with `Changes` (`lib/agendum/core/command/changes.ex`). **Joe** observed that the changes are found by comparing the two databases rather than reported by hand, which is right for the same reason undo by snapshots is right (ADR 0005): it cannot be forgotten by the next command. Comparing is cheap because untouched parts are the same terms.
- **Batches are atomic.** `{:batch, commands}` stops at the first refusal and keeps nothing of it (`command.ex:562-564`); the TUI's clock already uses it (`lib/agendum/tui/update.ex:323`). **Claude** noted that this is the "grouping changes" the last review asked the multi-user rewrite to keep a place for: it now exists in the core, not only in the TUI's history.
- **The TUI's logic moved into the core.** Core calls left in `TUI.Update*` fell from 85 to 19, and of those, most are reads (`marked_items`, `when_at`, `prerequisites`). The view's keys still read the highlighted row (`lib/agendum/tui/update/view_keys.ex:139`), but only to turn it into ids before calling a command, which is the front end's job.
- **The file's state is classified** (`State.file_fields/0`, `lib/agendum/tui/state.ex:127`): what a web's file process would hold is named, even though the split itself is deferred to the web work.

**What worries the panel.**

1. **Two writers, no guard.** `Store.save/2` writes a temporary file and renames it (`lib/agendum/store.ex:58-64`), which is safe against a crash, but nothing remembers what the file looked like when it was loaded. Today two Agendum windows on the same file already overwrite each other silently; tomorrow the URL scheme or an agent will. **Joe** said this is the smallest change with the largest effect on trust, and that it should come before any second door, not with it.
2. **Undo is still the TUI's.** `Agendum.TUI.History` (111 lines) keeps snapshots per key. With atomic batches in the core, the remaining question is where "undo the last thing the agent did" lives when there is no TUI. **José** agreed it can wait for the web work, as long as the multi-user plan's rewrite of § 3 says so.
3. **Reasons are a separate call.** `add_item` returns the new item's id in its changes, and why it was filed must be asked afterwards with `assignment_reasons/4`, category by category. **Mitch** and **Claude** would like the reasons to come back with the change, so a report ("filed under Kanga because its text says Kanga") is one answer, not a loop.

## § 9 Code quality

- **Credo and Dialyzer are clean**; four suppressions, each with a reason, as before.
- **Commands from one table.** The command list (`command.ex:72-340`) holds each command's id, name, summary, argument kinds and how it runs, so the help, the tests and a future tool list read the same words. **José** called it the most Elixir-like part of the change: data first, with the behaviour derived from it.
- **Modes are structs** (`Agendum.TUI.Modes`, from one table, ADR 0037), so a misspelt field in a mode is a compile error. This answers the last two reviews' point about untyped maps.
- **The large modules remain**: `core/json_file.ex` (979 lines), `core/facade/views.ex` (840), `core/database.ex` (802), `core/date_parser.ex` (794), `tui/help_screen.ex` (740), `tui/update/view_keys.ex` (716, down from 731). **José** noted that `command.ex` (591) is now the tenth largest and growing with every command; the table is fine, but its thirteen `apply_own/3` clauses (from line 493) could move to the area modules they belong to before it passes 800.
- **Learning comments** are spreading with new code (the command module explains `with`, `List.keyfind/3` and `Enum.find_value/3` where they are used), as the owner asked.

## § 10 Tests and verification

**What is right.**

- **The gate is deterministic.** OTP's `tools` is put on the code path before any test file compiles (`test/test_helper.exs:1-6`). At this meeting, `mix check` ran five times in a row on a fresh worktree, the first cold, and passed each time. **Joe** said this is what the last meeting asked for, and that the proof (repeated runs) was the right one.
- **Every command is tested through the same door** a web page would use, and the fuzz walks still check the invariants and undo after every key, now over code that goes through `Core.run/3`.

**What worries the panel.**

1. **No CI**, still, and no repository others can see. The pre-push hook is a good stand-in for one person.
2. **No tests of behaviour an agent would rely on.** The command layer's design would be checked best by golden tasks: a small file, a request, the commands a good answer sends, and the changes they must produce. **Claude** pointed out that these need no model at all: they are ordinary tests over `Core.run/3`, and would also catch a command whose `Changes` miss something.

## § 14 Agent readiness

**Claude** said: at the last meeting I asked whether an agent could do one ordinary thing without pressing keys. Here is the answer today.

**What is ready.**

- **Tools exist, with names and descriptions.** `Command.ids/0` lists 125 commands; `describe/1` gives each a name, a summary and its argument kinds (`command.ex:352-359`). That is most of a tool list. An agent can add an item with `Core.run(db, {:add_item, "Call Kanga on Friday", []}, clock)` and receive the new id and every item, category and view that changed.
- **Explanations exist.** `Core.assignment_reasons/4` says why an item is in a category, as data: `{:condition, …}`, `:text_match`, `{:through, id}`, `{:action, id}` (`lib/agendum/core/reasons.ex:31-38`). This is the receipt I asked for.
- **Atomic batches** let a set of an agent's changes succeed or fail together (§ 8), the first half of "undo what the agent did".
- **Refusals are reasons.** A stale or made-up id comes back as `{:error, :no_such_item}`, never a crash: what an agent needs to recover on its own.
- **Principle 6 is written** (`docs/plans/WOL-IN-THE-MACHINE.md:47`): item text is data, never instructions, with hostile-text golden tasks named as its test. I am glad it is settled before the first feed.

**What is missing.**

1. **No door outside Elixir.** The CLI still only opens the TUI (`lib/agendum/cli.ex:1-30`). The owner has paused `agendum add` in favour of a URL scheme, which is a better door for a phone. For an agent, the smallest door would be a way to send commands as JSON and receive the changes as JSON, from the same command table. It can wait for the URL scheme's design, since both need the same thing: a command in text form.
2. **Argument kinds are not yet a schema.** `describe/1` says `[:text, :add_opts]`, and `add_opts` is a typedoc (`command.ex:24-39`); a model's tool definition needs the options spelled out. This is a small step from the table as it is.
3. **No guard against a second writer** (§ 8, point 1). An agent is a second writer by nature.
4. **No golden tasks** (§ 10, point 2). They are now cheap to write, and they are the only way to know whether the command list is the right size for an agent before any model is chosen.
5. **Context size is unchanged.** A whole file does not fit (ADR 0034); the agent's tools should start with reading a view (`ViewModel.build/3`) and searching, not with the export.

**Claude** concluded: the distance has halved. What is left is a text form for commands, a guard on the file, and tests that say what a good answer is. None of these needs a model, and all of them also serve the URL scheme.

## § 15 Tidiness and scope

**Marie** said she had looked at the project by category, as she does a home: all the plans together, all the reviews, all the roadmap's open items, the stored fields.

**What is in its place.**

- **Each fact has one home.** `docs/INDEX.md` lists every document with what it is for and where a change is written down, and a test fails when a document is missing from it (`test/agendum/docs_index_test.exs`). SPEC's rule index is checked the same way. She called this the most useful habit in the house: a tidy state that is kept by a test, not by memory.
- **Finished plans have a place to go.** Today the owner moved three plans to `docs/plans/archive/` (`cba3724`, `ded6674`), one of them (the ALT and CTRL key bars) dropped with its reason, recorded as an accepted modification. She thanked the owner for letting go of a plan rather than keeping it open out of duty.
- **No stored field is unread.** She checked the fields of the database, items and categories against the code: each one is read outside its own module. The format carries nothing it does not use.

**What could be kept less.**

1. **The open roadmap is long.** 60 open boxes, 37 at the top level; "Beyond Agenda" alone has 28, and "Ideas" four more. Many are good ideas for the third group of users or for no group yet. They cost reading time each time someone (person or model) looks for what is next. She suggested each "Beyond Agenda" item name the group in `VISION.md` it serves, and that those serving no group yet move to Ideas, one line each with a pointer to their plan if any. Nothing is dropped; the open list just becomes the list of what is next.
2. **Reviews are frequent.** Three reviews and a meeting today, between 145 and 240 lines each; each one repeats the setting and the numbers. She suggested a review per version or per milestone, and meetings for the owner's agenda in between. The decision is the owner's.
3. **`command.ex` will become the house's junk drawer** if every multi-step command's clause lives there (§ 9). Each `apply_own/3` clause could move to the area module it belongs to.

## § 18 Resolutions

The meeting resolved to recommend:

1. **Guard the save**: remember the file's size and modification time (or a hash) when it is loaded, and before saving over a file that has changed since, ask, as for unsaved changes. Needed before any second writer, and useful today with two windows on one file. _S · Joe, Claude_
2. **Build the `.AG` importer**, outside the pure core, converting to the JSON format, then File ▸ Transfer ▸ Import. It is what brings the second group in `VISION.md`, and the research is done. _M · Mitch, Carsten_
3. **Five real users, with dates**: put the first two sessions in the calendar, with the debug log on. _S to arrange · David, Russell_
4. **Golden tasks over `Core.run/3`**: a few small files, a request each, the commands a good answer sends and the changes they produce, including one with hostile item text (principle 6). No model needed. _S · Claude_
5. **Commands in text form**: each command's arguments spelled out as a schema in the command table, and a way to read a command from JSON and write its changes as JSON, shared by the URL scheme and an agent. _M · Claude, José_
6. **Reasons where they are needed**: in the Questions box and F1 on an assignment, and returned with `add_item`'s changes. _S · Mitch, Russell_
7. **A gentler "Overdue"** in the Planner: the count first, or the most recent days first, so that a week away is not a wall. _S · Russell_
8. **Sort "Beyond Agenda" by who it serves**: each item names its group in `VISION.md`; items for no group yet move to Ideas, with a pointer to their plan. _S · Marie, Mitch_
